# Canonical configuration

`BursarConfig` is one strict versioned document. Pydantic defines the Python
contract, generates the published JSON Schema, and AJV validates the same
contract in JavaScript. Unknown fields and legacy shapes are rejected, and the
same document bills identically in both SDKs.

The top-level sections are organized by responsibility:

| Section | Purpose |
| --- | --- |
| `pricing` | Usage operations, measures, dimensions, and reusable rate cards |
| `credits` | Buckets, spending policies, grants, and display conversion |
| `entitlements` | Typed product features |
| `admission` | Reusable concurrency policies |
| `plans` | Product access, allowances, quotas, and policy references |
| `commerce` | Providers, offers, and auto-recharge guardrails |
| `catalog` | Catalog-wide settings such as the default signup plan |

Only `version` and `credits` are required. Fixed v1 accounting defaults to
`credit`, six decimal places, and half-up rounding, so authors do not need to
repeat that block. Plan `rank` defaults to `0`.

The canonical demo configuration below matches `base_config()` from the shared
sample code: prompta's two operations, one rate card, two credit buckets, two
entitlements, an admission policy, the `free`/`pro` plans, and Stripe offers
with auto-recharge guardrails.

:::note

This is the same canonical configuration the [quickstart](../quickstart.mdx)
publishes, shown in full. The quickstart uses a trimmed version with one
operation and no entitlements, admission, or commerce sections; the document
below is the complete shape.

:::

```yaml
version: 1
catalog:
  default_plan: free

pricing:
  operations:
    completion:
      measures:
        input_tokens: { unit: token }
        output_tokens: { unit: token }
        cache_read_tokens: { unit: token }
      dimensions:
        model: { type: string }
    execution:
      measures:
        jobs: { unit: job }
        compute_seconds: { unit: second }
      dimensions:
        model: { type: string }
  rate_cards:
    standard:
      operations:
        completion:
          rules:
            - when:
                model: { op: in, values: [gpt-4o, gpt-4o-mini] }
              charge:
                type: sum
                components:
                  - { type: per_unit, measure: input_tokens, rate: "0.0025", unit_size: "1000000" }
                  - { type: per_unit, measure: output_tokens, rate: "0.0100", unit_size: "1000000" }
                  - { type: per_unit, measure: cache_read_tokens, rate: "0.00125", unit_size: "1000000" }
          unmatched:
            action: charge
            charge:
              type: expression
              formula: input_tokens * 0.005 + output_tokens * 0.015
        execution:
          rules:
            - when:
                model: { op: eq, value: gpt-4o }
              charge: { type: per_unit, measure: jobs, rate: "0.04" }
          unmatched: { action: reject }

credits:
  buckets:
    promotional: { priority: 1 }
    purchased: { priority: 10 }
  default_bucket: purchased

entitlements:
  features:
    voice_mode: { type: boolean, default: false }
    max_context: { type: integer, default: 128000, minimum: 8000, maximum: 200000 }

admission:
  policies:
    default: { max_in_flight: 4 }

plans:
  free:
    display_name: Free
    rank: 0
    rate_card: standard
    allowed_operations: [completion]
    credit_allowance:
      amount: "10000"
      priority: 5
      window: { type: calendar, unit: month, count: 1 }
  pro:
    display_name: Pro
    rank: 1
    rate_card: standard
    allowed_operations: [completion, execution]
    features: { voice_mode: true, max_context: 200000 }
    quotas:
      daily_tokens:
        operation: completion
        measure: output_tokens
        limit: "500000"
        window: { type: calendar, unit: day, count: 1 }
        enforcement: block
        emit_at_percent: [80, 100]
    admission_policy: default

commerce:
  providers:
    stripe: { type: stripe }
  offers:
    pro_monthly:
      type: subscription
      display_name: Pro Monthly
      price: { amount_minor: 2000, currency: USD }
      providers:
        stripe: { type: stripe_price, price_id: price_pro_monthly }
      plan: pro
      billing_interval: { unit: month, count: 1 }
      cycle_grant:
        amount: "50000"
        bucket: purchased
        renewal: replace_previous
    credits_10k:
      type: topup
      display_name: "10,000 Credits"
      price: { amount_minor: 500, currency: USD }
      providers:
        stripe: { type: stripe_price, price_id: price_credits_10k }
      credits_per_unit: "10000"
      quantity: { minimum: 1, maximum: 10, default: 1 }
      bucket: purchased
      lot_behavior: separate_lots
  auto_recharge:
    eligible_topups: [credits_10k]
    balance_below: { minimum: "1000", maximum: "5000", default: "2000" }
    rearm_above: "20000"
    quantity: { minimum: 1, maximum: 10, default: 1 }
    limits:
      max_purchases: 5
      window: { type: calendar, unit: day, count: 1 }
      max_charge_minor: 5000
      cooldown: { unit: hour, count: 1 }
      max_consecutive_failures: 3
      failure_action: pause
```

All exact decimal values are strings; offer prices are integer minor units with
an explicit currency. Rate matcher operators must agree with their dimension
type: `prefix` is for strings, `range` is for numbers, and matcher values must
have the declared string, number, or boolean type. Expression charges may
reference only the measures declared by their operation.

For subscription-backed plans, explicitly setting `revision_policy` is
recommended. When omitted, subscription-backed plans use `next_renewal` and
other plans use `immediate`.

Credit bucket priorities and `credit_allowance.priority` share one ordering
namespace, with lower numbers consumed first. Priorities cannot collide. When
an allowance omits `priority`, it retains the legacy behavior of spending before
all buckets.

Validate before publication:

```bash
bursar config validate bursar.yaml
```

Use `--json` to receive native Pydantic diagnostics suitable for CI and editor
integrations.

## How configuration reaches the database

Publishing writes an immutable catalog revision; activating selects it.

| Step | API | Effect |
| --- | --- | --- |
| Publish a draft | `bursar.catalog.publish_draft(config, label)` / `publishDraft` | Validates the document and inserts a `published` revision; the live catalog does not change |
| Activate | `bursar.catalog.activate(version)` / `activate(version)` | Marks one revision `active`; exactly one active revision exists per tenant |
| Publish and activate | `bursar.catalog.publish_and_activate(config, label)` / `publishAndActivate` | One-shot: validate, insert, and activate |

Revisions are immutable and identified by a SHA-256 digest of the canonical
document: publishing a document whose digest matches an existing revision
reuses it instead of inserting a duplicate. Activation deactivates the
previous revision, records the activation in history, and schedules the plan
rollout for subscribers. `catalog.get_config()` / `getConfig()` returns the
active document as a validated `BursarConfig`, and `public_view()` /
`publicView()` projects the public subset.

For operations, the `bursar config` CLI covers the same lifecycle: `validate`
checks a file without applying it, `set` always creates a new version, `get`
prints the active config, `list` shows all versions (`*` marks the active
one), `activate` switches the active version, `diff` compares two versions,
and `schema` prints the JSON Schema.

## Signup account trigger

For immediate plan assignment and `account_created` grants, attach Bursar's
tenant-aware trigger function to the SaaS principal table and pass the
provisioned tenant slug:

```sql
DROP TRIGGER IF EXISTS bursar_account_created ON app.users;
CREATE TRIGGER bursar_account_created
AFTER INSERT ON app.users
FOR EACH ROW
EXECUTE FUNCTION bursar.provision_subject_account_on_insert('acme');
```

The hook resolves the active tenant, binds transaction-local tenant context,
assigns the active default plan, and applies eligible `account_created` grant
programs. The principal UUID must be available as `NEW.id`; host migrations
need no wrapper function or access to Bursar-owned tables.
