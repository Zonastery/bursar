# CLI and deployment

The `bursar` CLI is the operator interface for migrations, tenant lifecycle,
and the canonical configuration. Connection secrets come from environment
variables, never the command line:

| Variable | Required for |
| --- | --- |
| `DATABASE_URL` | Every command |
| `BURSAR_TENANT_ID` | `config` commands and `tenant bootstrap` without `--id` |

## Migrate

```bash
export DATABASE_URL=postgresql://...
bursar migrate
```

The command applies pending ordered SQL files, records checksums, and fails
if an already-applied file changed. A second run is a no-op.

## Tenants

Provision tenants with the same operator connection:

```bash
bursar tenant create acme \
  --id 018f7f5f-7b4a-7000-8000-000000000001 \
  --display-name "Acme"
```

`tenant create` generates the UUID when `--id` is omitted and prints it.
Change lifecycle state with `tenant status`:

```bash
bursar tenant status 018f7f5f-7b4a-7000-8000-000000000001 suspended
bursar tenant status 018f7f5f-7b4a-7000-8000-000000000001 active
```

For a deployment bootstrap, provision a tenant and publish its initial config
through one idempotent command:

```bash
export BURSAR_TENANT_ID=018f7f5f-7b4a-7000-8000-000000000001
bursar tenant bootstrap acme ./pricing.yaml \
  --display-name "Acme"
```

`tenant bootstrap` validates the config before provisioning. Tenant creation
and config publication are each idempotent, so the command is safe to retry
after an operational failure. Host applications should use these operator
commands instead of writing Bursar-owned tables.

## Config lifecycle

Catalog versions are immutable and managed per tenant through `bursar config`.
All subcommands require `BURSAR_TENANT_ID`:

```bash
bursar config validate ./pricing.yaml   # validate without applying (--json for CI)
bursar config set ./pricing.yaml         # publish + activate a new version (--label)
bursar config get                        # print the active version as JSON
bursar config list                       # list all versions (* = active)
bursar config activate 3                 # switch the active version
bursar config export 3                   # dump one version as JSON
bursar config diff 2 3                   # unified diff between two versions
bursar config schema                     # print the config JSON Schema
```

`config set` always creates a new version and no-ops when the payload is
identical to the active one — the command reports "No changes" and does not
churn versions. `validate`, `set`, and `export` accept `-` to read from
stdin. `list` marks the active version with `*` and shows labels and
timestamps; `diff` compares two canonicalized versions and `schema` prints
the JSON Schema for editor autocompletion and CI validation.

## Post-migration host SQL

Applications can add trusted, host-owned SQL after Bursar's bundled
migrations:

```bash
bursar migrate \
  --post-migrate-sql ./database/host-integration.sql \
  --post-migrate-sql ./database/scheduled-maintenance.sql
```

The option is repeatable and files execute in command-line order, under the
same advisory lock and transaction as pending Bursar migrations. A failure
rolls back the entire transaction.

Post-migration files are intentionally not added to Bursar's checksum ledger
and execute on every invocation. Keep them idempotent and under the host
application's source control. Only pass trusted files: they execute with the
database privileges in `DATABASE_URL`.

## A deployment workflow

Deploy in this order:

1. Run `bursar migrate` against `DATABASE_URL`.
2. Provision the tenant: `bursar tenant create <slug>` or the combined
   `bursar tenant bootstrap <slug> ./pricing.yaml`.
3. Publish and activate the canonical configuration — `bootstrap` covers
   this; otherwise `bursar config set ./pricing.yaml` followed by
   `bursar config activate <version>` if you are not activating the newest
   version.
4. Verify what is live: `bursar config get` and `bursar config list`.
5. Start or roll the application; the store and runtime bind
   `BURSAR_TENANT_ID` at construction time.
6. To roll back a bad config, re-point with
   `bursar config activate <previous-version>` — versions are immutable, so
   the prior document is still exactly as published.

For this greenfield cutover, drop and recreate the `bursar` schema in each
non-production environment before applying the baseline. There is no
compatibility or data-conversion migration.
